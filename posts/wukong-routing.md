## computeOptimalPath 实际做了什么

当前前端函数从起点开始，在剩余景点里选距离当前位置最近的一项，加入坐标序列并从待访问集合中移除。重复后，再追加固定终点，返回一条 Turf `LineString`。

这是最近邻贪心启发式。它实现了“生成一个访问顺序”，但函数名中的 Optimal 并不意味着数学上保证最优。

```text
起点 → 最近的未访问景点 → 下一个最近景点 → … → 终点
```

在合适的小数据集上，这种算法容易实现、响应快，适合作为路线草案。不过每一步局部最近，并不保证最终总距离最短，尤其当终点固定时，前面贪心选择可能让最后一段变得很长。

## 页面还悄悄选择了全部途经点

`planRoute()` 把除了起终点之外的所有取景地都作为 `waypoints` 传入。如果用户只想从一个景点去另一个景点，结果却要求把剩余景点全部访问一遍，问题首先是需求语义不匹配。

建议明确区分“起终点通行路线”与“多景点访问排序”，并让途经点来自用户实际选择。是否固定终点、是否允许返程、要不要访问全部地点，都应成为明确输入。

## 连线长度不等于驾车里程

Turf 的 `length` 计算这条经纬度折线各段的球面长度。它不知道道路、转向限制、隧道、单行线和通行时段。地图上看见一条连线，不代表真实世界有一条同样长度的路。

如果结果来自当前算法，适合称为“景点访问顺序建议”和“球面连线长度估算”。需要实际驾车路线时，应接入道路路由引擎或具有对应数据的服务，然后用返回的路线几何和距离展示。

## 后端为什么常常直接连接起终点

后端 `build_network` 把每对地点都连边，并用球面距离作为边权，构建完全图。再对完全图执行最短路径，通常会直接选择起点到终点的一条边。

原因是球面最短距离满足三角不等式：经第三点绕行不会比直接的最短距离更短。调用 NetworkX 本身没有错，图模型里没有道路约束才是结果不符合“导航”直觉的原因。

智慧校园项目使用真实道路顶点建图，回答的则是不同问题。两个项目里都有最短路径，不代表它们计算的是相同业务含义。

## 从原型走向可用规划

可以把流程拆成几个明确步骤：用户选取景点、确定起终点、估算访问顺序、为相邻地点请求真实路由，再合并路线与里程。交通时间需要来自实际路由数据，不能简单套用直线距离。

对于访问顺序，可使用成熟的优化工具或对启发式结果做局部改良，但应标注优化目标。例如“总出行时间最短”与“总距离最短”未必给出相同顺序。营业时间和每天可用时间又是进一步的约束。

## 建议的验证集合

| 输入               | 验证重点                       |
| ------------------ | ------------------------------ |
| 无途经点           | 只连接起点与终点               |
| 一个途经点         | 每个输入地点恰好访问一次       |
| 多个地点坐标重复   | 用 ID 区分，不能只依赖坐标查找 |
| 起终点相同         | 明确是闭环游览还是无效输入     |
| 用户删掉一个途经点 | 路线、总距离和列表同步更新     |

这篇复盘最重要的结论是：先为结果命名，再选择算法。准确表达能力边界，才能让用户依据结果做出合适的旅行决策。
